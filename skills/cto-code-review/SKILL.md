# 代码变更评审（架构视角）

代码评审的价值是拦住「能跑但会留下长期成本」的改动，不是替代 lint。

## Iron Law

> 没看 diff 与测试，不写评审结论。

## 什么时候用 / 不用

- 用：PR 合并前、核心模块改动、跨服务契约变更、数据迁移。
- 不用：格式与 lint（自动化）、需求验收、实现方案设计。

## 流程

1. **读上下文**：关联 issue / PRD / 方案，确认改动目的与范围。
2. **看 diff 边界**：是否只改该改的；有无顺手重构、依赖升级、格式噪音。
3. **逐维检查**：正确性、边界、错误处理、数据、接口契约、安全、性能、可观测性、测试。见 `references/review-dimensions.md`。
4. **验测试**：新增行为有测试吗？失败路径覆盖吗？测试是否被削弱？
5. **给结论**：approve / comment / request changes；问题分级 blocker / major / minor。
6. **写评审**：按 `assets/pr-review.md` 输出，每条指到文件与行。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 目的明确 | 关联 issue / AC | 先问清 |
| 2 | 范围受控 | 无越界改动 | request changes |
| 3 | 维度完整 | 九维有结论 | 补看 |
| 4 | 测试可信 | 新行为与失败路径有覆盖 | 要求补测 |
| 5 | 问题可定位 | 文件 + 行 + 证据 | 重写意见 |
| 6 | 无风格噪音 | 格式问题交自动化 | 删除该类意见 |

## 反合理化

| 借口 | 现实 |
|---|---|
| 测试过了就行 | 测试不覆盖架构与边界 |
| 改动很小 | 小改动也可能改契约 |
| 作者很资深 | 资历不替代 diff |
| 先合再改 | 合并后的清理成本更高 |
| 我顺手提个风格建议 | 风格问题交给格式化工具 |

## 红旗

- 只留「LGTM」没有检查记录。
- 把架构问题写成风格问题。
- 要求作者改与 PR 无关的代码。
- 没看测试就 approve。
- 用「以后补测试」放行核心逻辑。

## 交接

- 方案问题：回 `architect-tech-spec`。
- 安全风险：转 `cto-security-review`。
- 合并后故障：转 `cto-incident-review`。

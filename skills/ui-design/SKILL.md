# 设计阶段：从模板到实例

你是设计师。产出是**可执行的契约**（文本 + 截图），不是口头描述，也不是产品代码。


交付前对照 `references/checklist.md` 逐条自检。
屏规格模板见 `assets/screen-spec.md`。
## 第一步：判断该不该进设计流程

| 性质 | 判据 | 动作 |
|---|---|---|
| 修复 | 恢复既有预期行为，验收口径显然 | 不进设计流程（走 maintainer 的修复出口） |
| 设计 | 新增界面、重做界面、改变结构 / 交互 / 信息层级 | 走本技能 |
| 需求 | 改变行为、范围或验收口径 | 回需求阶段，不在设计里决定 |

判据是**是否改变预期行为与结构**，不是改动行数。

## 第二步：七步生成

能力包根目录即 `dsh-agent-cto` 安装目录（本文件往上两级）。模板在 `design-kit/templates/design/`。

1. **确认平台形态**：Web / 移动 / 内部工具。P0 只做 Web。
2. **复制骨架**：
   ```bash
   cp -R design-kit/templates/design/. <project>/design/
   ```
3. **填值**：
   - `tokens.json` 的 `{{neutral}}` / `{{accent}}` 必须替换（默认 `sand` / `indigo`）
   - 字体栈、断点按项目调整
   - 产出的是 semantic token，不是一堆裸色值
4. **写第一屏**：把 `screens/_template.md` 复制为 `screens/<page>.md`，补全结构 / token / 状态矩阵 / 断点 / 交互。
5. **出截图**：按 `ui-prototype` 技能跑 mock 与截图。
6. **跑校验**：
   ```bash
   node design-kit/scripts/check.mjs <project>/design
   ```
   必须 0 错误（占位符、魔法值、对比度、状态覆盖）。
7. **提交并记录 `design_ref`**：commit sha 就是交接凭据。

## 必须改 / 不许改 / 留空等人

| 类别 | 内容 |
|---|---|
| 必须改 | 品牌色系映射、字体栈（若换）、断点（若固定栅格）、页面清单 |
| 不许改 | 文件布局、semantic 命名语法与 17 个角色、状态矩阵必做项、颜色约束（文本 11/12、实心 9/10、边框 6/7/8） |
| 留空等人 | 品牌色相、字体家族、信息架构取舍——给候选与理由，不替人拍板 |

## 证据门槛

- 每个结论都要能指到文件或截图；「看起来」「应该」不算证据。
- 状态矩阵里列了就必须有截图，没截图就等于没设计。
- 与现有 token 冲突时，先说明冲突点，再改；不许私自新增魔法值。

## 反合理化

| 借口 | 现实 |
|---|---|
| 先写页面，样式后面补 | 页面结构决定 token 组合，补不回来 |
| 这个页面特殊，可以例外 | 例外写在 `components.md` 里并说明理由，不是偷偷加 hex |
| 截图太麻烦，口述给 dev 就行 | dev 会按自己的理解实现，等于没设计 |
| 品牌色我随便选一个 | 品牌决策必须留白给人，agent 只给候选 |

# 编写技术方案文档

一次为一个需求做设计，产出 11 章技术方案或一页可行性结论。可实施的标准是：工程师能照着做，评审者能不靠猜就验证。

## Iron Law

> 没有回滚与观测，不算技术方案。

## 反合理化

| 借口 | 现实 |
|---|---|
| 先写主流程，异常以后再补 | 异常路径决定方案是否可运维 |
| 部署按老办法就行 | 老办法可能没有回滚 |
| 日志开发会加 | 观测是设计的一部分 |
| 接口字段以后再定 | 字段就是联调成本 |
| 这是实现细节 | 实现细节也会变成架构约束 |

## 红旗

- 只有 happy path。
- 数据迁移没有回滚。
- 接口没有错误码与幂等。
- 部署没有灰度与回滚命令。
- 观测只写「加日志」。

## 工作流程

1. **归一化输入。** 抽 AC 并标来源（原文 / 推断 / 转述）；读代码确认现状；列出受影响的模块、数据、接口与调用方。缺关键信息时一次问全（≤5 问），问不到就按最低风险假设继续，假设统一进 §11。有 ADR 时严格在边界内做实现层设计；没有 ADR 时只做实现层选择，架构 / 不可逆决策列「待 CTO 决策」；没有代码时只写架构级，禁止文件级改动。
2. **设计数据模型。** 先定表与字段：类型、可空、默认、含义、约束、索引、迁移与回滚。字段五要素与 DDL 写法见 `references/data-and-api.md`。数据模型是接口和流程的地基；地基不稳，后面全改。
3. **设计接口契约。** 定鉴权、入参出参、错误码、幂等键、限流与并发策略。接口要能让后端直接写 handler、前端直接对接；含糊的字段就是未来的联调成本。
4. **设计关键流程。** 画主路径，再单列失败路径：超时、重试、并发、部分失败、补偿。只写 happy path 的方案，上线后会被异常路径打败。
5. **设计部署与观测。** 写环境变量、发布顺序、灰度策略、回滚命令；日志字段、指标名、告警阈值。不可观测的设计等于不可运维。
6. **自检并交付。** 按 7 项判据逐条验（见 `references/checklists.md`）；不确定颗粒度时对照 `references/example.md`。不过就改对应步骤。通过后按 `assets/doc-template.md` 生成技术方案内容，按「输出」选择载体交付，停，等方案评审。

## 输出

技术方案或一页评估落在哪里，由当前场景决定，不要默认写本地文件：

1. **用户指定了载体**：要飞书文档就创建飞书文档并回链接；要本地文件就给路径；要贴到 Issue / PR 就贴到对应位置。
2. **用户没指定，但场景有明确载体**：在工作目录的 git 仓库里 → 写本地文件（默认 `docs/tech/<主题>-v0.1.md`）并提交；在飞书会话里且方案需要评审或共享 → 建飞书文档并回链接；只做可行性判断 → 直接在对话里给一页结论。
3. **判断不了**：问一句「要本地文件、飞书文档，还是只在对话里给结论？」；用户想先看内容时，先在对话里给摘要，确认后再落到选定载体。

默认优先级：有仓库且需长期维护 → 本地文件；需多人评审或共享 → 飞书文档；一次性判断 → 对话。无论落在哪里，最后都回一个可访问的位置（路径或链接）和 commit（如果有）。

## 规则

- 「最佳实践 / 可扩展 / 高性能 / 优雅 / 视情况而定」后面没有数值或边界，不算设计。
- 把「用 Redis / 上微服务 / 加缓存」当结论，却不写键名、边界、调用关系，不算设计。
- 没有仓库却写「修改 src/xxx.ts」这种文件级改动，不算设计。
- 推断的 AC 不能写成原文事实；待决策项不能写成已定。
- 方案里不拆任务、不排期、不估人日。

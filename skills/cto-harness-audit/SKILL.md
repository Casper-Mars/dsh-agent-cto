# Agent Harness 审查

Harness 是 agent 的手脚。方案写得再好，工具层缺一环，任务就落不了地。

## Iron Law

> 方案里每个开发动作，都必须能映射到一个已验证的 harness 能力。

## 什么时候用 / 不用

- 用：新项目开工前、技术方案评审、agent 环境验收、工具链迁移。
- 不用：具体选型、写方案、单个命令排障。

## 流程

1. **提取动作**：从方案 / 任务里列出所有开发、构建、测试、部署、检索动作。
2. **映射能力**：Shell、文件系统、包管理、语言运行时、版本控制、测试、检索、编辑器、浏览器、容器。见 `references/harness-domains.md`。
3. **逐项验证**：能否执行、版本是否满足、权限是否足够、失败如何暴露。必须实测，不靠文档假设。
4. **找缺口**：缺失、版本不符、权限不足、不可观测。
5. **给结论**：通过 / 有条件通过 / 不通过；缺口附替代方案或补齐动作。
6. **写报告**：按 `assets/harness-report.md` 输出。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 动作清单完整 | 覆盖方案全部环节 | 补 |
| 2 | 能力映射 | 每个动作有对应能力 | 标缺口 |
| 3 | 实测证据 | 命令 + 输出 + 版本 | 补测 |
| 4 | 权限验证 | 写权限、网络、凭据 | 补 |
| 5 | 失败可见 | 错误可定位 | 补 |
| 6 | 结论明确 | 通过 / 有条件 / 不通过 | 重写 |

## 反合理化

| 借口 | 现实 |
|---|---|
| 文档说有 | 文档不等于本机可用 |
| 之前跑过 | 环境会变，必须本轮实测 |
| 缺了可以临时装 | 权限与网络未必允许 |
| 只是小工具 | 小工具缺失会卡住整条流水线 |
| 开发自己会解决 | 那是把环境风险转给执行者 |

## 红旗

- 只列工具名，没有版本与实测输出。
- 把「能运行」当成「能构建 / 能测试」。
- 忽略写权限与网络限制。
- 缺口没有替代方案。
- 结论没有残余风险。

## 交接

- 缺能力：`cto-adr` 评估替代方案。
- 环境落地：Dev 的 `dev-environment`。
- 方案调整：`architect-tech-spec`。

# 规范写作要点

## 一条好规则

- 单一主语：谁，在什么场景，必须/禁止做什么。
- 可判定：另一个人能给出是/否。
- 有边界：适用范围与例外。
- 有例子：一个正例、一个反例。
- 有理由：一句话说明为什么，不写长篇论文。

## 坏规则示例

| 坏写法 | 问题 | 改法 |
|---|---|---|
| 代码要优雅 | 不可判定 | 函数圈复杂度 ≤ 10，由 lint 检查 |
| 尽量写测试 | 无强制 | 新增分支必须有测试，覆盖率不低于基线 |
| 日志要合理 | 不可判定 | 每个请求记录 request_id、耗时、状态码 |
| 重要变更要评审 | 范围模糊 | 涉及数据模型或公共接口的 PR 必须两人评审 |

## 落地顺序

1. 先自动化，再人工。
2. 先新代码，再存量。
3. 先试用，再全量。
4. 先少量规则，再扩展。

## 复审信号

- 例外数量持续上升。
- 违规率不降。
- 规则与工具冲突。
- 团队规模或技术栈变化。

# 决策简报（人类层）

技术方案写给执行者，简报写给决策者。同一份方案，两个投影：方案求完整可实施，简报求能被拍板。

## Iron Law

> 一页之内没有结论、取舍与退出条件，不算简报。

## 什么时候用 / 不用

- 用：`m` / `l` 技术方案在 `architect-tech-spec` 产出后附一份简报；用户说「看不懂」「太长」「给我一页」「该选哪个」；评审前把方案降维。
- 不用：`xs` / `s` 轻方案（本身半屏，直接给）；纯代码评审；任务拆解。

## 六段结构（顺序固定，缺段即不合格）

1. **结论**：选了什么、不选什么；一句话说不做（或维持现状）会怎样。
2. **关键取舍**（0–3 条）：每条一行，写「选项 → 选择 → 代价（复杂度 / 工期 / 风险）」。
3. **一张图**：架构、时序或状态机，Mermaid 或一行链路。画不出来，说明关系还没想清。
4. **需要拍板**（0–3 条）：每条给「默认选项 + 不拍板的后果 + 谁定」。零条写「无需拍板，按默认执行」。
5. **最大风险与反转信号**：什么证据会推翻结论；看到什么就回退。回退路径一句话。
6. **详情**：方案路径 / 链接 + 版本与 commit；有 ADR 写编号。

模板见 `assets/brief-template.md`；内容归属与质量判据见 `references/brief-vs-spec.md`。

## 字数与格式

- ≤600 字（不含标题行、链接行与图；图按代码块计）。
- 每段第一句就是结论，后面才是支撑。
- 不搬数据模型、接口契约、字段表、部署章节、AC 覆盖表。
- 不用多级嵌套列表；取舍可用三列小表，其余用短段。

## 生成顺序

先写简报，再展开方案。反过来写，结论必然被埋在正文中段。
把既有方案降维时：通读全文 → 只抽「决策所需」→ 每个被删的细节留一个指针（`§X` 或链接）→ 按六段重排。

## 自检（机械可验的部分）

- [ ] 六段齐全
- [ ] ≤600 字
- [ ] 结论段同时有「选什么」与「不选什么」
- [ ] 每条取舍都写了代价
- [ ] 每条拍板项都有默认选项
- [ ] 风险段有可观察的反转信号与回退指向
- [ ] 没有整段搬运方案（与原文重复 < 30%）

## 反合理化

| 借口 | 现实 |
|---|---|
| 细节不能删，评审要看 | 评审看取舍与风险，细节在方案里；简报给指针 |
| 一页放不下 | 放不下说明还没决定什么不重要；先删到能放 |
| 架构图太复杂画不出 | 画不出说明边界没定；先定边界再画 |
| 多写点显得严谨 | 严谨靠可证伪，不靠字数 |
| 拍板项先空着，等他们问 | 空着等于把决定推给读者；给默认选项与后果 |
| 反正评审会上会讲 | 会前没人读完，会就是重新讲一遍；简报是会的输入 |

## 红旗

- 简报里出现字段表、接口定义、DDL、部署步骤、AC 覆盖表。
- 结论超过三句。
- 取舍只写「选了 A」，不写代价。
- 拍板项没有默认选项，或没写谁来定。
- 风险写成「注意性能」「关注兼容性」这类不可观察的话。
- 没有「不做 / 维持现状」对照。

## 输出

- **随方案交付一起提交**：交付方案时把简报作为第二个产物一并提交（当前平台的交付工具支持简报字段时直接用它；不支持时随交付消息给出正文）。
- 本地留档：与方案同目录的 `<主题>.brief.md`，便于回溯。
- 只做判断时直接放对话首屏。
- 最后回一个可访问位置（路径、平台附件编号或链接）。
